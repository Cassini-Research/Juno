# Juno Docs Style Guide

## Product naming

Use **Juno** as the public product name. User-facing docs should not expose internal package names. Developer docs may mention literal repo paths only when required.

## Launch posture

Write for the final public launch moment: final app, website, launch video, Product Hunt announcement, and public docs released together.

## Tone

Precise, calm, concrete, and product-grade. Prefer mechanism over hype. Do not write generic AI copy.

Avoid phrases such as:

- revolutionary
- unlock the power
- seamless AI productivity
- game-changing
- magic, unless clearly informal and not technical
- works everywhere
- production-ready unless tied to the final verified launch

## Page rules

Each page must have one reader intent. User pages explain product behavior. Developer pages explain build/run/test/contribution paths. Trust pages explain actual data and privacy mechanisms.

## Claim rules

Every public claim must be supported by one of:

- latest repo/code truth
- final product behavior
- uploaded final screenshot/video
- verified command output
- explicit product decision from Jas

If unverified, leave it as an internal verification item.

## Media rules

Screenshots must show final launch UI. Videos reinforce text; they do not replace written instructions. Each video embed needs a summary and a written flow.

## Privacy wording

Explain what data exists, where it lives, how long it is retained, how to delete/export it, and what the limits are. Do not use privacy slogans without mechanism.

## Diagrams

Each diagram must have one point, a caption, and a takeaway. Architecture diagrams should be layered: product flow first, implementation details later.
